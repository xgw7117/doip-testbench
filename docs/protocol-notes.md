# 协议笔记：DoIP / UDS 实现要点

这份笔记记录实现过程中真正踩过的点，而不是标准目录的复述。每条结论都可以在本仓库的代码或用例里找到对应位置。

---

## 1. DoIP 帧结构

```text
+--------+--------+--------+--------+--------+--------+--------+--------+
| ver(1) | inv(1) | payload type(2) |        payload length(4)        |
+--------+--------+--------+--------+--------+--------+--------+--------+
|                              payload ...                              |
+-----------------------------------------------------------------------+
```

- `ver` 常见取值：`0x02`（ISO 13400-2:2012）、`0x03`（2019）。
- `inv` 必须是 `ver` 的按位取反。**先校验 inv，再校验版本**：如果 inv 不互补，说明发送方和接收方对帧边界的理解已经错位，此时回一个 Generic NACK 后应关闭连接。
- `payload length` 只统计 payload，不含 8 字节头。上限由 ECU 能力决定，测试台默认 64 KiB。
- TCP 是字节流：一次 `recv()` 可能拿到半帧、一帧或三帧。解析必须带缓冲，**不能假设一次 recv 等于一帧**。

代码：`src/doipbench/doip/frame.py`

## 2. 路由激活（0x0005 / 0x0006）

请求 payload（7 或 11 字节）：

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| source address | 2 | Tester 逻辑地址 |
| activation type | 1 | `0x00` 默认、`0x01` WWH-OBD、`0xE0` 中央安全 |
| reserved | 4 | 全 0 |
| OEM | 4 | 可选 |

响应 payload（9 或 13 字节）：

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| tester address | 2 | 回显请求中的源地址 |
| entity address | 2 | DoIP 实体逻辑地址 |
| response code | 1 | 见下表 |
| reserved | 4 | 全 0 |
| OEM | 4 | 请求带则响应带 |

| 响应码 | 含义 | 本项目的触发条件 |
| --- | --- | --- |
| `0x00` | 源地址未知 | 源地址为 `0x0000` 或不在白名单 |
| `0x01` | 所有 socket 已占用 | 已激活连接数 ≥ `max_concurrent_sockets` |
| `0x02` | 与已激活的源地址不同 | 同一连接换了一个 tester 地址 |
| `0x03` | 源地址已注册 | 同一连接重复激活同一地址 |
| `0x06` | 不支持的激活类型 | activation type 不在 `00/01/E0` |
| `0x10` | 接受 | 正常路径 |

**易错点**：`0x02` 和 `0x03` 都是「同一 socket 上重复激活」的分支，区别只在源地址是否相同。很多实现把它们合并成一个，TC8 用例会直接抓出来。

## 3. 诊断消息（0x8001 / 0x8003）

```text
0x8001: source address(2) | target address(2) | UDS request/response
0x8003: source address(2) | target address(2) | NACK code(1)
```

| NACK 码 | 含义 | 典型场景 |
| --- | --- | --- |
| `0x02` | 源地址无效 | 未完成路由激活就发诊断 |
| `0x03` | 目标地址未知 | target 不是本 ECU 的逻辑地址 |
| `0x04` | 诊断消息过长 | 超过 `max_data_size` |
| `0x08` | 传输协议错误 | payload 不足 4 字节，缺 SA/TA |

**关键区分**：

- **UDS 负响应**（`0x7F SID NRC`）是**正常诊断响应**，装在 `0x8001` 里发回去。
- **DoIP 诊断 NACK**（`0x8003`）表示**这一帧根本没送到 UDS 层**。
- **Generic NACK**（`0x0000`）是**帧级**错误，payload 为「原始 payload type + NACK code」。

三者混用会导致测试用例「明明该 7F 却收到 8003」的经典误判。

## 4. UDS 时序

| 参数 | 含义 | 本项目取值 |
| --- | --- | --- |
| P2 | 收到请求到首个响应的最大时间 | 50 ms |
| P2\* | 发送 `0x78` 后允许的延长 | 5000 ms |
| S3 | 非默认会话无请求的超时 | 5000 ms（测试中可配置） |

`0x10` 正响应中的 P2/P2\* 编码：P2 单位 ms，P2\* 单位 10 ms。响应 `50 03 00 32 01 F4` 表示 P2 = 0x0032 = 50 ms，P2\* = 0x01F4 × 10 = 5000 ms。

S3 超时后必须**同时**做两件事：回默认会话、清除安全访问等级。只做前者会让「超时后仍能写 DID」这种漏洞漏到量产。

## 5. 五大服务

### 0x10 会话控制

| 会话 | 值 | 说明 |
| --- | --- | --- |
| default | `0x01` | 上电默认，只读 |
| programming | `0x02` | 刷写 |
| extended | `0x03` | 写入、安全访问 |
| safety system | `0x04` | 安全件 |

请求 2 字节，多一字节或少一字节都回 `0x13`。

### 0x27 安全访问

- 子功能奇数请求 seed，偶数发送 key。
- 默认会话下请求 → `0x7F`（服务在当前会话不支持）。
- 未请求 seed 直接发 key → `0x24`（请求序列错误）。
- key 错误 → `0x35`，累计到上限 → `0x36`，锁定窗口内 → `0x37`。
- 已解锁后再次请求 seed，返回**全 0 seed**，tester 应跳过 key 直接认为已解锁。

### 0x22 / 0x2E

- `0x22` 支持一次读多个 DID：`22 F1 90 F1 87`，响应按请求顺序拼接。
- DID 列表必须是偶数个字节，否则 `0x13`。
- `0x2E` 在默认会话返回 `0x7F`（不是 `0x33`）；扩展会话但未解锁返回 `0x33`。**顺序很重要**：先判会话，再判安全。
- 写入长度与 DID 定义不符 → `0x13`；DID 不存在或只读 → `0x31`。

### 0x19 读取 DTC

| 子功能 | 请求 | 响应结构 |
| --- | --- | --- |
| `0x01` 数量 | `19 01 mask` | `59 01 mask format count(2)` |
| `0x02` 列表 | `19 02 mask` | `59 02 mask [DTC(3) status(1)]*` |
| `0x04` 快照 | `19 04 dtc(3) rec` | `59 04 dtc status rec numID [DID(2) len data]*` |
| `0x06` 扩展数据 | `19 06 dtc(3) rec` | `59 06 dtc status rec data` |
| `0x0A` 支持的 DTC | `19 0A` | `59 0A mask [DTC(3) status(1)]*` |

状态掩码是**按位与**：`mask=0x08` 只返回 `confirmedDTC` 置位的记录。`mask=0x00` 返回空列表，但仍要回 `59 02 00`，不能当成错误。

## 6. 抑制正响应位

子功能字节的 bit7 为 1 时，**成功不回复**，失败仍要回 `0x7F`。

这对测试框架的影响：`request_uds()` 不能无条件等待响应，否则每次 suppress 用例都要等满超时。本项目在 YAML 里用 `expect_no_response: true` 显式声明，测试侧用 0.3 s 的短超时断言「确实没有响应」。

## 7. ISO-TP 与 DoIP 的分段差异

| | ISO-TP (ISO 15765-2) | DoIP (ISO 13400-2) |
| --- | --- | --- |
| 承载 | CAN 帧，单帧最多 7 字节 | TCP 字节流 |
| 分段 | 首帧 / 连续帧 / 流控帧，需 SN 校验 | 依靠 4 字节长度字段 |
| 流控 | 接收方回 FC（CTS/WAIT/OVFLW） | TCP 自身流控 |
| 典型长度 | ≤ 4095 字节 | 受 `max_data_size` 限制 |

所以「DoIP 不需要 ISO-TP」是对的，但网关把诊断从以太网转到 CAN 时仍然要做一次 ISO-TP 分段。本仓库的 `transport/isotp.py` 就是为这个场景准备的，含序列号回绕（15 → 0）处理。

## 8. SOME/IP 长度字段

`Length` 从 **Request ID** 开始计数，等于 `8 + len(payload)`，**不包含** Message ID 和 Length 字段本身。

写成 `16 + len(payload)` 是最常见的错误：解析端会多读 8 字节，把下一条消息的头吞掉。单元测试 `test_length_field_excludes_header_prefix` 专门锁这条。

SOME/IP-SD 的固定端口是 **30490**，Message ID 固定为 `0xFFFF8001`（service `0xFFFF` + method `0x8001`）。

## 9. gPTP 的两个细节

- 报文头的第一个字节高 4 位是 `transportSpecific`，低 4 位才是 `messageType`。直接拿整字节比较会永远匹配不上。
- `correctionField` 是 **signed 64-bit**，单位 2⁻¹⁶ ns。转成 ns 要除以 65536，不是除以 1000。

## 10. 面试常问的五个问题

**Q1：为什么 DoIP 用 TCP 还要自己处理粘包？**
TCP 只保证字节顺序，不保证消息边界。DoIP 用 4 字节长度字段显式分帧，接收端必须缓存并按长度切分。

**Q2：路由激活的作用是什么？**
让 ECU 知道「哪个逻辑地址通过哪个 socket 发诊断」，同时做资源准入（socket 数上限）和安全校验。未激活的 socket 发诊断必须拒绝。

**Q3：0x27 的 seed 为什么不能固定？**
固定 seed 等于没有安全保护，重放即可解锁。真实 ECU 用 HSM + 随机数，且 seed 与 key 的映射由 OEM 的 seed/key DLL 提供。

**Q4：0x2E 写失败应该返回哪个 NRC？**
取决于失败原因：会话不对 `0x7F`、未解锁 `0x33`、DID 不存在或只读 `0x31`、长度不符 `0x13`、写入过程失败 `0x72`。不能一律 `0x22`。

**Q5：怎么证明你的测试是有效的？**
每个正例都有对应的负例；NRC 覆盖表在 `docs/test-matrix.md`；协议实现的分支覆盖率 88%；CI 在三套 Python 版本上跑同一份用例。
